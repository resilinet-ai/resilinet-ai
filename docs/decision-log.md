| 2026-11-14 | RAI-API-KEYS | Project API keys and the CI gate (FR-06.1, threats S-02, D-03). Keys `rai_<prefix>_<secret>`: 12-character prefix, 32-byte secret, only its SHA-256 stored (no slow hash: nothing to guess); expiry required, 1-90 days, checked in the database; revocation is the only change (trigger) and keys are never deleted; audited. Scopes runs:start and runs:read; a key acts only on its own project (other projects 404), every other endpoint is 403, and account endpoints refuse keys. Lookup through one SECURITY DEFINER function that returns a key only while its tenant and project are active and its creator is still an active admin or engineer. Runs record the key and its creator (triggered_by); the audit actor is the key. 120 requests/min per key, in-process. `rai run` starts a plan by name (newest version) or id, polls to a verdict and exits 0/1/2 like `rai validate`; key from RAI_API_KEY only; plain http refused except to localhost; stdlib HTTP client. Composite action at the repository root installs from the lockfile (`uv run --locked --no-dev --inexact`) and passes the key by environment; CI job "CI gate" runs it against a live API and worker | Argon2 for key hashes; keys owned by the tenant rather than a user; GitHub OIDC workload identity; httpx in the CLI; a separate action repository; Docker action | Spec: keys hashed, shown once, expiry required, project-scoped (Data Model, threat S-02). A key that outlives its creator would be an orphaned credential. The stdlib client adds no dependency to CI. A root action.yml can be pinned by commit SHA like any other Action, and the CI job proves it blocks on a real failing contract. OIDC stays the post-MVP option (spec) |
| 2026-11-14 | RAI-LINEAGE | Lineage (FR-04.1). Engineers declare asset inputs (asset X derived from asset Y, optional transform_ref) in `asset_inputs`: same project only, cycles refused by a trigger serialised per project with an advisory lock, removable (audited), never updated. A run pins each target's whole upstream graph at queue time (at most 100 hops per item, else 422). Each step records lineage_edges in its own transaction: every pinned hop, the target into the run, and each reference dataset into the run, with the digest of every frame the worker read. Upstream assets are read only when the test definition maps them to a worker connector (`upstream`); unmapped ones are hops without a digest. Digest rai-frame-digest/1: SHA-256 over the connector-normalised text frame, columns and rows sorted, one JSON line per row; `rai validate` reports the same value (content_sha256). lineage_edges adds step_key, from_name and from_rows to the Data Model's columns so reference datasets and the step are recorded; to_asset_id null means the run | Digest of the file bytes; ordered row digest; reading every upstream asset through the target's connector; free-form lineage without declared assets; OpenLineage now (FR-04.2) | Spec acceptance: a run's graph shows every hop and the SHA-256 of its inputs. File bytes differ between CSV, Parquet and PostgreSQL for the same data, and a PostgreSQL read has no row order, so the digest is taken over normalised content. Upstream sources can live behind different connectors, so the operator maps them explicitly instead of guessing. Pinning keeps old runs stable when declarations change (tested) |
| 2026-11-14 | RAI-RUNS | Runs, job queue and worker. A run pins plan, test-case (with definition), asset and contract versions with SHA-256 at queue time and executes from the pins only. State machine queued, preflight, running, evaluating, then passed or failed, with refused, aborted and error, enforced by a trigger that also freezes finished runs and pinned inputs. Each plan item is a step; its observations and its run_steps row commit in one transaction (the retry guard), and the verdict is computed from recorded steps, so a resumed run reaches the same verdict. Queue in PostgreSQL: FOR UPDATE SKIP LOCKED, 5-minute lease renewed between steps, at most 3 attempts with back-off, then the run ends in error with the last error. The worker logs in as rai_worker (member of rai_app; one extra RLS policy to see and lease every tenant's jobs) and refuses to start otherwise. Contract-rule steps read only through connectors the operator installs on the worker. Freshness defaults to the batch's newest row, as `rai validate` does; `freshness_reference: now` for live feeds. Unsupported test types and missing connectors refuse the run at preflight. Idempotency-Key: same request returns the same run; a key reused for a different request is 422 (keys never expire) | Celery or Redis queue; recording observations as they stream; tenant-supplied file paths; as_of = run clock by default; 24-hour idempotency window | Architecture: PostgreSQL is the queue, no broker. FR-06.2 acceptance (killing the worker mid-run does not duplicate observations) tested by killing the worker inside a step's transaction and resuming on a second worker. A run on the clock defaulted every replayed SandboxBank batch to stale (found in testing). Keys that never expire are stricter than the Data Model's 24 h and need no clean-up job |
| 2026-11-14 | RAI-DEFINITIONS | Projects, assets, contracts, test cases and plans (Data Model section 3). Every row carries tenant_id under RLS, and foreign keys include tenant_id (and project_id where the parent must be in the same project), because PostgreSQL checks foreign keys without RLS. Contracts, test cases, plans and plan items are immutable: no UPDATE/DELETE grant for rai_app, plus a refusing trigger. Contract versions come from the contract's own `version:` and must increase, with the same contract name per asset; the stored spec is the canonical JSON and its SHA-256, identical to what `rai validate` reports, plus the source exactly as published. Test-case and plan versions are numbered by the server per name (test_cases and test_plans gained a `name` column for that). Projects are the only mutable resource here: ETag from row_version, If-Match required (428 missing, 412 stale); archived projects accept no new definitions. Lists use cursor pagination (limit at most 200). Write roles exactly as the endpoint catalogue: projects A and E; assets, contracts, test cases and plans E only. Columns for later tables (environments B-22, connectors, scenarios B-26) exist without foreign keys until those land; plans refuse scenario items until B-26 | Mutable definitions with history tables; server-numbered contract versions; offset pagination; plain foreign keys | Spec: runs pin exact versions and must be replayable; the contract's own version is what reports and the key history use (transactions_raw@3), so the server must not renumber it; the tenant_id foreign keys close a cross-tenant reference path that RLS alone leaves open (tested). Members list (B-16) stays unpaginated until tenants need more than 200 members |
