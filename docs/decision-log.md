| 2026-11-21 | ROBUSTNESS | FR-09.3, design approved by the author. A `robustness_check` test case reads a feature table, and RAI perturbs it itself: `noise` (a numeric feature times 1 + scale·z), `missing` and `unknown_category`, each on a share of the rows. Every draw is a SHA-256 of the seed, the perturbation, the column and the row's position. Each variant is scored by the system under test's model, posted only to the `score_url` of an `http` target on the environment's allow-list (migration 0017). The batches carry the features only, never ids or labels. The clean table and every variant are evaluated with FR-09.1's code (counts, intervals, minimum samples) and judged on each metric's degradation against `max_drop`. A model whose identity changes between calls, a wrong number of scores, or too little data is an error. SandboxBank gains `sandboxbank model features` and the model-api service (profile `model`), and its image now carries scikit-learn | The system under test perturbs and scores, and RAI compares the scores files; RAI loads and runs the model; numpy's random generator; judging each variant against absolute targets | If the system perturbs, RAI has to trust the labels of its own evidence. Running the model puts scikit-learn and a pickle loader inside RAI, against TEVV-METRIC. SHA-256 draws give the same variant on any platform and library version, and need no new dependency. A model that is merely good on clean data says nothing about robustness: what matters is how much a perturbation costs |
