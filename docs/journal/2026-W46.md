26. **Update (B-22):** environments and the target allow-list. 27. **Update (B-23):** the chaos agent: the protocol's seven fault types through Toxiproxy and a socket proxy that allows only the Docker verbs it needs, with the agent's own target checks and a state file written before every action. A CI job injects every type on SandboxBank and checks the effect and the recovery (FR-07.1 acceptance), and that the socket proxy refuses container creation, exec, image pulls and volumes. Learned: the end-to-end run caught a race in which the expiry loop undid an injection in progress, and showed that service labels alone would match containers in another Compose project; both fixed and covered by unit tests.
28. **Update (B-24):** signed fault requests and the second preflight. The worker checks the run's environment, its ceiling and the allow-list for every target in the blast radius, takes the label from the registry, and signs the request with its Ed25519 key. The agent applies only requests signed by a key it trusts, fresh and for its own environment, once per run and step; it applies its own ceiling, open-fault cap and blast-radius rule whatever the request says. Onset, refusals and errors are recorded as observations, once even when a step is retried. The unsigned development mode is gone: CI signs with a throwaway key and checks that unsigned, forged, replayed, expired and other-environment requests are refused. Decided: the agent takes one dependency, `cryptography`, installed by hash (RAI-CHAOS-SIGNED). Learned: keying the replay guard on run and step, rather than a nonce, turns a worker retry into a 409 that carries the onset, so the retry needs no extra state.
29. **Update (B-25):** the independent watchdog and the kill-switch drill. A second container from the agent's image reverts any fault past its request time + duration + grace, including one the agent left mid-injection, under the same cross-process lock as the agent (or without it if the agent hangs; reverts are idempotent and record who made them). The drill, in CI, kills the agent with payments-api stopped and waits for the watchdog to bring it back, then runs `kill --all` with no RAI API or database in the stack. Decided: RAI-CHAOS-WATCHDOG. Learned: the latency and timeout toxic was named only after Toxiproxy accepted it, so a crash in between left a toxic no revert could find; it is now named before the fault is recorded.
30. **Update (B-26):** chaos scenarios. Engineers publish scenario versions (a blast radius and faults in order); reviewers approve or reject them, append-only, and never their own (API and database). Plans hold scenario items; a run starts only with every scenario approved and an environment, and pins the version and the approval. The worker re-checks the approval and every fault, then signs, injects, holds and reverts each fault in order, recording onset and revert; a retry after a crash injects nothing twice. Decided: RAI-SCENARIOS; RTO and RPO are the next item. Learned: a test that drained leftover runs with a chaos-enabled worker ran another test's scenario against its agent; leftovers are now drained by a worker without a key, which refuses them.
31. **Update (B-26b):** recovery measured in scenario runs. A scenario's recovery plan names allow-listed probe and ledger targets and RTO/RPO objectives; the worker reads the ledger head before the first fault, probes after the last revert until every probe holds healthy, and records RTO (from the fault's onset) and RPO (from the ledger head) as observations; a missed objective, no restoration or lost ledger rows fail the step. Decided: RAI-RECOVERY-MEASURE. Learned: the head read before the faults has to be stored, or a worker retrying after a crash would measure RPO from a point after the fault.
32. **Update (B-27):** scenario-level blast radius and the refusal suite. Signed fault requests now name their scenario version, and the agent holds every fault of a scenario step to the version and radius already recorded for it, reverted faults included. docs/refusals.md catalogues every refusal by layer with its proving test, and a unit test keeps it true. Decided: RAI-SCENARIO-RADIUS. Learned: the B-24 radius rule compared only open faults, and scenario faults are never open together, so it could not catch a scenario widening its reach between faults.
33. **Update (FR-08.3):** post-recovery consistency checks. The worker now runs `consistency_check` test cases: it reconciles a target (the warehouse facts) against a declared upstream source (the ledger) through worker connectors, snapshotting the source and retrying within a window while the target catches up, and records missing, duplicated, unexpected and mismatched keys as observations. A plan of scenario then check shows the system came back correct, not just healthy. Decided: RAI-CONSISTENCY. Learned: the source keeps growing during the check, so 'missing' is judged against a snapshot taken at the start, while 'unexpected' and 'mismatched' use a fresh read.
